# 运营手册：每天 20 分钟，把它维持成一份可信的海洋日报

这份手册以每天约 20 分钟为起点；待审核积压、来源改版或同步故障时需要额外时间。海洋领域要特别核对海区、机构与预印本状态，不能因流程自动化就省略审核。

---

## 1. 一条资料在系统里经历了什么（你要知道，才好排查）

```
信源 → 采集 → 判重 → 预筛（宽召回） → 两次独立评分 → 结构化（分类/标签/事实）
     → 写作（中文标题/摘要/推荐理由） → 归组（同一事件） → 精选门槛
     → 公开读取层 publication/ → 网页 / RSS / API / MCP / 日报
     → stepx 首次快照 / 变更账本 → 幂等入库 pending → 人工审核 → App
```

- **预筛**只判断「是不是海洋的事」，宽召回，宁可多留。
- **两次评分**独立打，和 ≥ 2×门槛才进精选；两次差很多说明这条判断不稳，值得人工看一眼。
- **归组**把同一件事的报道合成事件；不同来源的同一件事只占一个精选席位。
- **日报**不调模型，按规则从当天精选里编；所以日报质量 = 当天精选质量。

排错顺序：**信源 → 采集（有没有抓到）→ 分析（有没有过预筛）→ 评分（多少分）→ 发布（为什么没公开）**。后台「内容」页点开单条能看到每一步的状态。

## 2. 每日清单（20 分钟）

### 早上（日报出刊后）

1. 打开日报，扫一遍标题。问三个问题：
   - 有没有把**政策文本**写成「发布了一个研究」？（政策与论文是最容易混的两类）
   - 有没有把**预印本/会议摘要**写成「已发表」？
   - 海区、机构、船名有没有明显不对？
2. 抽查 3 条，点进原文，核对摘要里的数字和海区。
3. 看到错的：后台「内容」→ 找到条目 → 改标题/摘要，必要时撤下。同步后核对 stepx 的实际条目与审核状态；不能只看 AIHOT 页面已改。
4. 查看最后同步成功时间、失败记录、接收端落库/队列状态与 pending 积压。无新增时累计推送数不增长属正常，结合任务触发记录判断。
5. 新内容通过前核对原文链接、原文日期与摘要；访客和会员均不得读到 pending。

### 中午（5 分钟）

- 看「全部动态」里有没有低质条目（旅游、招生、会议报名）。有就把它加到 `industry/prompts/prefilter.md` 的 BLOCK 例子里，或直接给信源降级/暂停。
- 看 `/admin/sources` 有没有 `failing`。

### 晚上（5 分钟）

- 看「候选池」里接近门槛但没进的条目（评分 50–58）。如果里面有好东西，说明门槛偏高；如果全是水文，说明评分提示词需要补噪声例子。

## 3. 内容质量红线（海洋领域专属）

| 红线 | 为什么 | 怎么防 |
|---|---|---|
| 海区张冠李戴（南海写成东海、CCZ 写成南海） | 读者一眼看出来，信任直接归零 | 摘要必须保留原文海区名；`rules-domain.md` 里已写标准译名 |
| 机构错配（NOAA 的研究写成 NASA） | 海洋机构多、缩写像 | 机构词典与提示词可辅助检查；仍对照原文核对，不能把自动规则视为准确保证 |
| 预印本当定论 | 海洋论文从预印本到正式发表常改结论 | 评分提示词要求区分「预印本/已接收/已在线」；人工复核 |
| 政策文本断章取义 | 协定文本差一个限定词意思全变 | 政策类只引用原文短句，不做转述式结论 |
| 旧文当新闻 | 期刊卷期日期常在未来或滞后 | 核对 publishedAt 原文日期和原文实际上线状态；updatedAt 是同步更正时间，不得拿来展示为新闻发布日期 |
| 图片误导 | 海洋图片极易「看起来像」 | 摘要不得仅凭图片推断地点/物种/结论 |

**一条经验**：凡是标题里出现「首次」「最大」「唯一」「创纪录」，点进原文确认原文是否真的这么写、范围是什么。模型很喜欢替论文加这类词。

## 4. 撤回、更正与来源方请求

- **来源方要求下架**：后台把该条 visibility 设为 withdrawn，保留记录。整个信源需停止采集时先暂停，再分别核对已公开条目；暂停采集本身不代表旧内容已撤下。
- **论文撤稿/更正**：找到条目 → 人工改摘要并注明「已于 X 日更正/撤稿」；必要时撤下。
- **自己写错**：修正标题/摘要并核对下一轮 stepx 更正；影响结论、数字或来源的改动注明更正日期与原因，已进入日报的同时更新更正记录。
- **批量问题**（某个信源连续出错）：先暂停信源，再看 `prefilter` / `structure` 提示词是否需要补规则。

### stepx 更正和撤回核对

新增、更正、撤回及代表稿变更通过快照/变更账本同步，nextSince 是不透明 ax1 游标。HTTP 409 snapshot_required 表示要重建快照；保留人工备注与审核记录，不把错误当作同步成功。

按 30 分钟任务周期配置的服务，撤回后在约定时限内确认 App 不可见；来源方紧急下架时同步检查两端并由 stepx 管理员立即软下架，不等下一次任务。只查最近 7 天不足以覆盖老内容。

仅 tags/story/body 或来源全文许可等扩展字段变化可能未写入账本。主动 push 已有独立 24 小时周期对账：每轮增量后用剩余页数预算重扫精选，reconcile_cursor 不覆盖 sync_cursor；积压时对账可能跨多轮完成。拉模式需接收端自己定期启动完整快照对账，建议每日检查完成情况。

来源撤销再分发许可后，对账中的 bodyText=null 必须清空 stepx 旧正文。完整成功后才比较遗留条目，禁止根据失败的部分快照批量删除。异常时看 [STEPX_INTEGRATION.md](STEPX_INTEGRATION.md) 的恢复与验收流程。

## 5. 信源维护

### 周检（10 分钟）

```bash
# 本地跑一遍体检（会抓真实网络）
cd /srv/ocean-bundle/oceanhot
python3 ../tools/verify_sources.py --json /tmp/sources-report.json
```

脚本在同级 tools，工具和完整站点的目录关系见 [DEPLOY.md](DEPLOY.md)。看报告的 total（条数）、withDate（有日期条数）和 newest（最新时间）；这是探测结果，还需核对站内采集与处理。

- `newest` 超过 120 天 → 信源可能已停更，考虑暂停。
- withDate=0 → 检查日期解析与来源原文，确认缺失时间的实际发布行为；不得填造日期来让条目入选。
- 摘要普遍为空 → 论文类正常，但意味着模型只能靠标题判断，门槛要更高。

### 加一个新信源

1. 先在 `tools/verify_sources.py` 的 `SRC` 里加一条，跑 `--only <id>` 验证。
2. 验证通过后，在后台「信源 → 新建」照抄配置，**先点预览抓取**，确认三件事（是文章、日期对、摘要不空）。
3. 再决定 `tier`：
   - `T1`：官方一手（NOAA、部委、研究所、同行评议期刊）
   - `T1_5`：准官方（MBARI、Scripps、学会、开放获取期刊）
   - `T2`：媒体与综合（ScienceDaily、Mongabay）
4. 新源前 3 天盯着，出错就暂停。

## 6. 成本控制

- 后台「模型与评测」：看每一步的调用次数与 token。异常升高通常是某个源突然回灌大量旧文，或归组在反复重试。
- 后台「设置 → 付费请求上限」：给模型、X、公众号、Jina 各设日上限。**先设上限再推广**。
- 冷启动阶段建议：
  - 只开 T1 + T1_5，T2 留 3 个。
  - `MODEL_CALLS_ENABLED=true` 但把 T2 的 `interval_minutes` 调到 360 以上。
  - 先不接 X 和公众号（按请求计费，最容易失控）。

## 7. 周报/月报与专题

- 周报、月报从日报汇编，模型只写总述和栏目导读。周报适合发公众号/小红书做「一周海洋大事」。
- 专题用「主题页」（`/topics`）：ENSO、海洋热浪、深海、极地、蓝色经济……每个主题页本身就是一个可分享的落地页。
- 想做「南海专题」「北极航道专题」这类更垂直的，不要新建一套系统：在 `industry/topics.json` 加一个 `field` 主题，用标签收条目即可。

## 8. 每周复盘（30 分钟，决定下一步）

回答四个问题，写在一张纸上：

1. 这周哪 3 条阅读量/转发最高？它们共同点是什么？
2. 哪 3 条我后悔发了？为什么？
3. 有没有读者在反馈里重复问同一个问题？（那就是下一篇课程/推文/产品的选题）
4. 本周新增/暂停了哪些信源？门槛要不要动？

把这些记录积累 4 周，再判断是否有足够证据制作付费产品；反馈数量、实际使用和支付意愿分别记录，不能互相替代。
