# 方案复盘：当前能力、已发现缺口与验收边界

本文区分四类信息：产品方案、代码中的实现、历史测试陈述和目标环境实测。方案写进文档、检查器 self-test 成功、界面能打开，都不能替代真实服务验收。2026-10-23 本轮修订记录见 [ITERATION_2026-10-23.md](ITERATION_2026-10-23.md)。

## 1. 最大的缺口是同步状态，而不只是页面

此前模块把文章 timeline_at 与 article_id 当同步游标。审计发现：

| 问题 | 实际后果 | 本轮方案 |
|---|---|---|
| 拉取接口按倒序查小于游标的旧内容，同步骨架却保存最终游标作下轮起点 | 首轮看似成功，第二轮新增拉不到 | 首次精选快照后续接内置变更账本 |
| 推送按文章 timeline_at 正序前进，旧文章更正时该时间不一定变 | 更正、晚入精选及代表稿变化可能漏掉 | 使用精选账本事件与不透明 ax1 游标 |
| 列表只查当前公开精选 | 已撤回记录被过滤，不能从同一列表发现撤回 | 账本投递 tombstone 与代表稿变化 |
| 以不存在 ID 的单条 tombstone 当撤回测试 | 未证明已同步条目真的会下架 | 验证先同步、再撤回、再自动下架 |
| 先返回 200，再在函数中异步写库 | 函数结束后可能永久丢数据 | 事务提交或可靠持久入队成功后才确认 |

接口仍使用 stepx 内容契约的 `stepx.ocean.v1` 字段结构；nextSince 改为服务器拥有的不透明 ax1 游标。旧时间游标返回 409 snapshot_required，客户端需要重新建立快照并对账，不能静默清空或误认为完成。快照结束时也保存 nextSince，下一轮从账本继续。

主动推送逐页投递，每页 2xx 后提交持久游标。可靠性还依赖 stepx 接收端的唯一约束、版本比较、事务、审核策略与任务互斥，不能只在发方宣称“已幂等”。

## 2. 当前协议仍有明确限制

主要新增、标题/摘要更正、撤回与代表稿变化由账本覆盖；只有 tags、story、body 或来源全文许可等扩展字段改变时，可能没有新事件。主动 push 增加独立 reconcile_cursor/reconciled_at，24 小时对账周期到期后重扫精选，每轮先追增量，再使用剩余页数预算对账，绝不覆盖主 sync_cursor。拉模式仍需接收端安排周期完整重核。积压会推迟对账完成，不能承诺每个字段即时同步。

完整对账成功前不能根据部分快照批量下架本地内容。保留人工备注与审核记录，恢复公开也按审核策略处理。接收端需允许可信完整对账刷新同版本扩展字段，同时防止旧快照复活新撤回内容。

默认正文关闭；打开后仍需来源明确允许再分发、条目 syndicate 许可与 body_mode=full。来源撤销权限时，对账传回的 null 应清空接收端旧正文。站内全文许可不自动等于可向合作方再分发的许可。

这些行为必须在真实 stepx 表与函数上验证。文档中的字段名与抽象持久化函数不代表线上已经存在，尚未取得证据的事项保持待验证。

## 3. 验签与配置不是“写过示例就完成”

原 webhook 示例允许把已解析对象 JSON.stringify，再拿重建字符串验签，与原始字节要求矛盾。本轮示例只接受平台提供的原始 Buffer 或字符串，验签成功后才解析 JSON；无原始请求体时拒绝并修复平台配置。

原 /admin/sync 临时保存只改 API 进程，不能持久轮换 token；本轮移除保存表单与 admin/config 写接口，配置统一写回 .env，再由 Compose 重建相关容器。restart 不会重新读取 env_file。Compose 已将 ADMIN_SYNC_TOKEN 透传给 web 服务器用于管理接口转发，密钥不发送给浏览器。

升级迁移 0091–0095 更新主同步与独立对账状态，丢弃旧 timeline_at/article_id 推送进度后重发首次快照；不会删除内容、审核或会员数据，接收端需验证重放幂等。

## 4. 历史材料能证明什么

| 材料 | 能支持 | 不能支持 |
|---|---|---|
| sources-report.json | 保存了当时 31 个源的探测记录 | 今天依然可抓、生产采集成功、模型已处理 |
| demo-entries.json | 当前 54 条演示条目的结构与阅读样例 | 已完成 stepx 真实入库、审核、权利核对 |
| 以前对话中的 typecheck/build/模块测试结果 | 当时报告执行过这些检查 | 本轮或目标服务器的代码也已通过 |
| 检查器 --self-test | 本地假服务上的检查器逻辑 | 真实 AIHOT 与 stepx 端到端联调 |
| 真实地址上的契约检查器 | 脚本覆盖的鉴权、结构、分页等基础接口行为 | 全量无遗漏、第二轮增量、webhook 落库、会员隔离 |

此前 README 与对话中的模块测试条数不一致；本轮不再复制固定的“6/6”或“7/7”作为当前结论。测试结果以实际命令、对应版本和输出为准。

本地结构为 D:/GALGAME 下并列的 oceanhot、ocean-pack、tools。ocean-pack 现附 tools/ 下的安装器与契约检查器；完整维护脚本在同级 tools。只克隆上游拿不到这些脚本。配置统计为 31 个源、29 份提示词和 54 条演示数据；配置数量不等于健康信源数量。

## 5. 内容判断与校准

来源可访问不等于内容准确，模型打分也不等于编辑判断。初期保留人工审核，核对来源、日期、海区、机构、数字与预印本状态。

旧校准方案只导未选记录，且人为平衡“该选/边缘/不该选”后把指标当真实分布，无法代表线上精确率。本轮改为：

- 120 条开发集用于覆盖难例、改提示词和门槛。
- 30 条独立随机 holdout 来自固定时间窗口的完整候选流，包括已选、未选和预筛拒绝。
- 标注时隐藏模型决定；开发集与留出集分别报告，不为凑比例改标签。
- 看过留出结果后继续调参，下一次需要新留出集；小样本结果只作初步验证。

当前门槛与价格都保持待验证假设，不伪造校准结果、账单或读者反馈。完整步骤见 [CALIBRATION.md](CALIBRATION.md)。

## 6. 产品和运营边界

AIHOT 公开站、RSS 与 API 免费可读，stepx 的会员价值要来自人工解读、可靠审核、专题组织、归档和服务，不能依赖同一份摘要的独占性。中文一手源是可深耕的方向，但来源公开内容本身不是独占素材。

PLAYBOOK 的价格、转化率和八周安排是可调整的试验计划，不是市场证据。专业身份、渠道和授课能力不能凭方案替运营者认定；课程、采访和推广按真实资源安排。

运营主体、联系方式、条款和收费规则仍需运营者确认，不能因为已有模板就标成合规完成。中文站改版、来源下架、模型调用失败与恢复演练都需长期运维。

## 7. 完成标准

“海洋知识星球服务已完成”至少需要同一部署版本的证据：

1. 四个常驻服务运行、setup 成功退出，公开入口与管理入口实测可用。
2. 真实来源采集与模型处理成功，质量经人工核对。
3. stepx 首次完整快照、重复处理、后续新增、更正、撤回与代表稿变化均通过。
4. webhook 验签与可靠持久化、超时重试、重启恢复、409 重建通过。
5. 待审核不可见，访客/非会员/会员/管理员读取范围正确。
6. 周期对账、备份与隔离恢复演练有记录。
7. 运营信息、服务承诺与实际交付一致。

只完成文档或本地代码调整时，结论应写“实现已调整、相关实测待完成”，不能替这些验收打勾。
